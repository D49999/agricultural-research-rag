# AgRAG 技术亮点与项目总结

> 一句话：把散落在 PDF、扫描件、网页里的农业科研资料，做成一个**能自证来源**的多模态问答助手。
>
> 本文记录项目的架构取舍、可复用的工程做法、以及实测数据支撑的结论。与 `README.md` 的差别是：
> README 面向使用者，本文面向**维护者/面试/答辩**，重点解释「为什么这么做」和「哪里容易踩坑」。

---

## 1. 项目定位与边界

**解决的问题**：农业技术资料的形式极不统一——部委发布的 `.md/.pdf` 方案、论文 HTML、扫描件、随文图表。通用关键词搜索既读不懂表格，也找不到图。

**系统做的事**：

1. 把异构资料统一成「结构化 Markdown + 图片」；
2. 文本与图像分别向量化、分别检索；
3. 由 Agent 根据问题语义决定查哪一路，并给出带文件与页码的引用。

**明确不做的事**（避免过度承诺）：

- 不做 PDF 直接解析（`DocumentRouter` 只收 `.md/.markdown/.txt`），PDF 必须先过 MinerU OCR 或 `pdf_to_txt.py`；
- 不做在线模型下载（本地模型一律 `local_files_only=True`，必须预置缓存）；
- 不把图像结果混进文本 Chroma 集合或 RRF 融合。

## 2. 系统架构

```
          PDF / 扫描件                    随文图片
              │                              │
        MinerU OCR                     (Markdown 内引用)
              ▼                              │
     结构化 Markdown ──► DocumentRouter ─────┤
              │                              │
        TextParser（版面块）                  │
              │                              ▼
   StructureAwareChunker              Qwen3-VL-Embedding-2B
   + src/agri 元数据抽取                       │
              ▼                              ▼
    Chroma: agri_rag              Chroma: agri_rag_images
              │                              │
      ┌───────┴────────┐                     │
      ▼                ▼                     │
  Dense(向量)      Sparse(BM25)               │
      └───────┬────────┘                     │
           RRF 融合 ──► (可选) Reranker        │
              │                              │
              └──────────┬───────────────────┘
                         ▼
              LangGraph ReAct Agent（工具路由）
                         ▼
            FastAPI（SSE 流式）/ Streamlit
```

三条路径互相独立，任何一条都能单独压测：

| 路径 | 入口 | 关键模块 |
|------|------|----------|
| 入库 | `scripts/ingest_*.py` / `POST /v1/ingest` | `text_parser` → `chunker` → `src/agri` → `chroma_store` |
| 文本问答 | `POST /v1/query`、`/v1/query/stream` | `understand_query` → `hybrid_retriever` → `rag_agent` |
| 图片检索 | `POST /v1/images/search` | `qwen_vl_embedding` → `image_store` |

## 3. 技术亮点

### 3.1 结构感知切分：表格不可分割

`src/document_parser/chunker.py`

普通按长度切分会把一张表从中间截断，模型只能看到半张表。`StructureAwareChunker` 先由 `TextParser` 把 Markdown 解析成带类型的 `ParsedBlock`（标题 / 段落 / 表格 / 公式 / 列表 / 代码），再按类型决定能否合并：

- **表格、公式作为原子块**，超长也不切；
- **标题不单独成 chunk**，而是写入后续块的 `header_context`，保证片段脱离原文后仍知道「属于哪一节」；
- 六种策略可切换（`fixed/sentence/paragraph/markdown/recursive/semantic`），默认 `semantic`。

这一条直接决定了「表格问答」能不能做——也是 `scripts/evaluate.py --chunk-ablation all` 能对比出差异的原因。

### 3.2 两个中文陷阱：token 估算与 overlap

同样的文件里还有两个只有跑中文才会暴露的坑，都已修掉并留了注释：

| 问题 | 原来 | 现在 |
|------|------|------|
| token 估算 | `len(text.split())/0.75`，中文没有空格 → 1000 字算成 1 个 token → 整篇挤进一个 chunk | CJK 按 `1.5 字/token` 折算，拉丁文仍按空格分词 |
| 重叠截取 | `text.split()[-n:]`，中文切不动 → 整段带进下一块 | CJK 占比 ≥30% 时按字符截取 |

**这是典型的「英文能跑、中文全废」型 bug**：不报错，只是检索效果莫名其妙地差。判断方法很朴素——入库后看 chunk 数是否与语料体量成正比。

### 3.3 Agentic RAG：把检索能力暴露成工具

`src/agent/rag_agent.py` + `src/agent/tools.py`

没有把「检索→拼接→生成」写死成一条链，而是用 LangGraph `create_react_agent` 让模型自己选路：

| 工具 | 何时用 |
|------|--------|
| `knowledge_base_search` | 默认文本检索，自动做农业槽位过滤 |
| `knowledge_base_search_structured` | 条件明确时显式传 `crop/disease/region/year/doc_type` |
| `knowledge_base_search_with_filter` | 限定某一份文件内检索 |
| `multi_round_search` | 复杂问题多子查询合并去重 |
| `image_search` | 视觉需求，走独立图像集合 |
| `query_rewrite` | 把口语问题拆成检索友好的子查询 |

工程上的关键点是**工厂模式**：`build_retrieval_tools(retriever, llm)` 在启动时绑定检索器，而不是用模块级全局变量，因此工具可被单测直接构造，也不会在 import 时产生副作用。

流式部分用生成器统一出口：`stream_query()` 逐步 `yield` `tool_start / tool_done / answer`，HTTP 层只负责包成 SSE（以 `[DONE]` 结束），前端与一次性接口共用同一套事件。

### 3.4 混合检索：RRF 融合 + 可插拔精排

`src/retrieval/hybrid_retriever.py`

- 稠密（Chroma 向量）与稀疏（内存 BM25）各自召回，用标准 RRF（k=60）融合，避免两路分数尺度不可比；
- 精排是可选环节（`ENABLE_RERANK`），默认关闭——CPU 上 0.6B 重排器的延迟换不来确定的收益，先关掉保证可测；
- **修复过一个隐蔽 bug**：`dense_weight or settings.dense_weight` 会让 `0.0` 被默认值覆盖，做消融时「权重设为 0」实际没生效，指标全是假的。改为显式 `is None` 判断，并补了回归测试。

> 教训：可配置项用 `or` 兜底默认值，等于把 `0`、`""`、`False` 都当成「没传」。

### 3.5 农业领域语义层：纯规则，离线，零成本

`src/agri/`（约 1100 行）+ `config/agri_lexicon.json`

把「农业」变成一个可计算的对象，四个模块职责清晰、互不依赖模型：

| 模块 | 职责 | 关键设计 |
|------|------|----------|
| `lexicon` | 词典、别名归一、实体识别、分词增强 | 长词优先（`小麦条锈病` 不被拆成 `小麦`+`锈病`）；保护品种名（`郑单958`）；**ASCII 别名整词匹配**（`tea` 不能命中 `instead`） |
| `metadata_extractor` | 文档/chunk 级元数据 | 文档级以「文件名 + 正文前部」为准；chunk 级先看自身命中，再继承文档单值；阈值保守，**宁可少标不可错标** |
| `filters` | 过滤条件规范化 | 一套 dict 同时服务 Chroma `where` 与 Python 侧 BM25 匹配 |
| `query_understanding` | 槽位/意图/年份/扩展 | 只抽「明确出现」的槽位；过滤过严由检索层兜底放宽 |

产出字段：`crop/crops`、`disease`、`pest`、`pesticide`、`region`、`growth_stage`、`variety`、`year`、`doc_type`、`authority_level`（1 标准/审定 > 2 方案/规程 > 3 论文 > 4 科普）。

几个踩过的坑，已写进规则里：

- 文档级 `crop` **优先取标题**，否则「小麦-玉米轮作」类正文会让主题作物漂移；
- 多食性害虫名里的作物前缀不算作物（`棉铃虫` ≠ 棉花，`甜菜夜蛾` ≠ 甜菜）；
- 英文别名必须整词匹配，避免子串误报。

### 3.6 同一套过滤条件，两条检索路径都必须吃到

这是本项目最容易被写错的地方：Chroma 能用 `where`，内存 BM25 不能。如果只给稠密加过滤，融合结果里会混进稀疏召回的无关文档。

做法是**一份规范化 dict，两种翻译**：

```python
{"crop": ["水稻"], "disease": "稻瘟病", "year_min": 2020}
   ├─ build_chroma_where()  → {"$and": [{"crop": {"$eq": "水稻"}}, ...]}
   └─ metadata_matches()    → 逐条比对 metadata（含旧数据多值兼容）
```

配套的**可解释性**同样重要：

- `retrieve_with_info()` 返回 `RetrievalOutcome(documents, filters, relaxed)`；
- 条件过严导致两路零召回时，自动回退全库检索并置 `relaxed=True`；
- 工具返回里带 `applied_filters` / `filter_description`，系统提示词要求「`relaxed=true` 时必须先说明未找到完全匹配资料」。

这样「过滤」不会变成静默失败：要么精确命中，要么明确告诉用户「这是相近内容」。

### 3.7 跨模态图像检索：独立集合，不做假融合

图像固定用本地 `Qwen3-VL-Embedding-2B` 编码，文本查询也由**同一个模型**编码到同一向量空间，因此「用一句话找图」是真正的跨模态匹配，而不是「给图片打标签再搜标签」。

`ImageChromaStore` 只做余弦相似度，`page_content` 存图片的 alt/caption 供 LLM 引用，`metadata` 存绝对路径。

**为什么不合到文本集合里**：实测文本向量与图像向量分布差异大，强行 RRF 会让图像结果被文本稀释。交给 Agent 按语义选择工具，效果更稳，也让两条链路可以独立演进。

### 3.8 回答可信度：把「边界」写进提示词

`_build_system_prompt()` 里有一组农业专用硬约束，这不是修辞，是产品要求：

1. 生产建议必须说明**适用作物、区域、生育期、年份**；资料没写就写「资料未注明」，禁止把单一地区结论泛化；
2. **农药剂量/稀释倍数/安全间隔期/残留限量**只依据检索到的标准、标签、登记资料回答，并注明发布机构与年份；没有权威依据时明确说「知识库中无权威依据」，提示核对当地植保站——**不凭模型记忆给剂量**；
3. `relaxed=true` 时必须先声明「未找到完全匹配的资料，以下为相近内容」；
4. 引用旧标准/旧规程要提醒可能已更新。

同时工具返回结构里带 `source` / `page` / `block_type` / `header_context` / 农业元数据，答案末尾统一附来源，做到**每句话可回溯到具体文件的某一页**。

### 3.9 工程化运行时：三个真实的线上问题

`run_server.py`、`src/api/main.py`、`src/embeddings/qwen_embedding.py`

| 现象 | 根因 | 处理 |
|------|------|------|
| 跑完一两轮问答后前端提示「无法连接到远程服务器」，进程却还在 | Windows 默认 Proactor 事件循环 + 同步阻塞问答，IOCP 里堆积失效连接，`accept` 抛 `WinError 64` 后监听循环退出 | Windows 改用 `SelectorEventLoop` |
| 思考期间 `/health` 超时，像服务挂了 | 同步推理占满事件循环 | `asyncio.to_thread` + 全局锁：问答串行、事件循环始终可响应 |
| 本地 embedding 慢到不可用 | CPU 上用 fp16，每层都要做精度转换 | 按设备选精度：GPU `float16`，CPU `float32` |

另外，所有重型单例（两个 store、retriever、agent）都在 FastAPI `lifespan` 里构建一次，路由通过依赖注入复用——**绝不在请求里加载模型**。BM25 是内存索引，启动时从 Chroma 最多重建 1 万条，入库后重建，这也是「改完元数据必须重启」的原因。

### 3.10 数据运维：非破坏、幂等、先 dry-run

农业索引会反复调整规则，脚本必须「可以随便跑」：

| 脚本 | 作用 | 安全设计 |
|------|------|----------|
| `backfill_agri_metadata.py` | 给旧 chunk 补农业元数据 | 默认 dry-run；只改 metadata、不动向量；`--apply/--overwrite/--prune` 分档 |
| `reembed_collection.py` | 换 embedding 后端后重刷向量 | 默认 dry-run；只重算向量，保留文档 |
| `fetch_zh_literature.py` | 抓部委公开技术方案为 Markdown | `_sources.json` 记录已抓 URL，重复跑自动跳过 |
| `cleanup_unused_images.py` | 清理无引用图片 | 必须 `--dry-run` 先看 |

> 为什么必须有 `reembed_collection.py`：Chroma 不记录「向量是哪个模型生成的」。换了 embedding 后端还沿用旧库，等于把两种向量空间混在一起，相似度会静默失真——**不报错，只是结果变差**。

## 4. 关键设计取舍

**Q1：为什么文本和图像用两个集合，而不是统一多模态索引？**
分布差异大，融合会互相稀释；而且两者的「正确答案」形态不同（段落 vs 图片+说明）。分开后 Agent 可以按需调用，失败也能分别定位。

**Q2：为什么农业语义层坚持纯规则，不交给 LLM？**
① 每个请求都要跑，规则是微秒级、零成本；② 元数据一旦被 LLM 幻觉污染，会污染整个索引且难以回滚；③ 规则可单测、可 diff、可解释。LLM 只用在真正需要语言能力的地方（改写、总结、润色）。

**Q3：为什么默认关掉 Reranker？**
CPU 环境下 0.6B 重排器是纯延迟成本；先建立**不含精排的基线**，才能量化精排到底带来多少收益。当前 top-1 失败率 37%，正是它该上场的地方，但要先测再说。

**Q4：为什么过滤「宁少勿多」？**
chunk 的 `crop`/`growth_stage` 都是单值，硬过滤容易把正确文档直接踢出 top-10（实测直述集掉 3 条、口语集掉 3 条）。当前策略是：只抽明确出现的槽位，零召回就放宽，并把这个事实告诉用户。

**Q5：为什么用 `semantic` 默认切分？**
农业方案有清晰的一/二级标题结构，按结构切能保留「第几章讲什么」的上下文；纯长度切分会把「防治措施」的前半段和后文割开。

## 5. 评测：怎么做的，结论是什么

### 5.1 数据集怎么来的

不是拍脑袋写题，而是**从语料里反向出题**：

1. 6 个子任务并行，每组 6 篇，从原文逐字摘 `quote` 再写题；
2. 脚本校验：`quote` 必须是原文子串，答案里的数字必须按序出现在原文；
3. 剔除原文残缺（只剩表格单元格）的文档 → 覆盖 35/36 篇；
4. 分三层：**70 条直述**（回归）+ **30 条口语化**（真实效果）+ **10 条拒答**（幻觉检查）。

负例题单独成文件，因为 `evaluate.py` 会把「没检索到」一律算 miss——**评测工具的默认语义决定了文件必须分开**。

### 5.2 基线（562 chunk / semantic 1024 / 本地 embedding / 无精排 / 无过滤）

**直述式（70 条）**

| 方法 | R@1 | R@3 | R@10 | MRR@10 |
|------|-----|-----|------|--------|
| Hybrid（Dense+Sparse+RRF） | 90.00% | 100% | 100% | 0.9500 |
| 仅 Dense | **91.43%** | 100% | 100% | **0.9524** |
| 仅 Sparse | 82.86% | 100% | 100% | 0.9095 |

**口语化（30 条）**

| 方法 | R@1 | R@3 | R@5 | R@10 | MRR@10 |
|------|-----|-----|-----|------|--------|
| Hybrid | **63.33%** | **83.33%** | **93.33%** | **96.67%** | 0.7417 |
| 仅 Dense | 56.67% | 76.67% | 90.00% | 96.67% | 0.7039 |
| 仅 Sparse | **63.33%** | 80.00% | 93.33% | 93.33% | **0.7444** |

### 5.3 结论

1. **直述已饱和，口语才是瓶颈**：直述 K=3 就 100%，口语 R@1 只有 63%——问题是「排不准」不是「找不到」。优化重心应放在 top-1 排序与词面归一。
2. **口语场景 BM25 ≈ Dense**：真实问法更依赖「小麦/蓟马」这类字面词；Hybrid 的 R@5 最高，说明融合主要改善中段。
3. **超长文档挤占 top-k**：`2026_小麦秋冬种技术明白纸.md` 独占 99/562 chunk（17.6%），11 条非 top-1 口语题里 9 条的 top-3 出现它 → 需要同源配额或 MMR。
4. **近似重复版本互相抢答**：直述 7 条非 top-1 全是版本/区域差异（2023/2024 番茄潜叶蛾、2024/2025 果树冻害、全国版 vs 西南版），稳定排第 2 → 需要年份/区域仲裁。
5. **硬过滤提升精度、损伤召回**：口语集 MRR@3 0.711→0.728，但 R@10 96.7→90.0 → `crop` 应匹配多值 `crops`，`growth_stage` 默认不硬过滤。
6. **别名覆盖仍有缺口**：`西红柿→番茄`、`豆角→豇豆` 已通，`送嫁肥`、`闷棚` 等农事俗语未收录。

### 5.4 为评测修的两个 bug（值得单独记）

| bug | 表现 | 修法 |
|-----|------|------|
| `final_k` 固定 5 | Recall@10 实际只看了前 5 条 | `max(k, settings.final_k)` |
| 权重 `or` 默认值 | `--dense-weight 0` 不生效，消融对比失真 | 显式 `is None` |

> 评测代码本身也会说谎。**先验证指标能反映真实行为，再相信指标。**

## 6. 已知局限

- **PDF 不在检索链路里**：`DocumentRouter` 只认 md/txt，UI 的 PDF 上传按钮实际会失败，必须先 OCR；
- **别名/俗语覆盖不全**：规则词典靠人工维护，长尾农事用语仍会漏；
- **时间/区域仲裁缺失**：同一技术的多版本方案只能靠相似度排序；
- **精排未启用**：基线不含 rerank，最优配置尚未确定；
- **过滤器粒度粗**：`crop`、`growth_stage` 为单值，多作物文档会漏；
- **后端与前端耦合**：`frontend/app.py` 硬编码 `http://localhost:8000`，改端口不生效；
- **负例题策略待定**：模型会先声明「知识库未找到」，但仍可能用互联网资料补充——是否允许「标注来源的补充」是产品决策，不是技术缺陷。

---

## 7. 优化路线

| 优先级 | 方向 | 预期收益 |
|--------|------|----------|
| P0 | RRF 后加同源配额（每来源 ≤N 块）/ MMR | 直接缓解超长文档垄断 top-k，口语集提升空间最大 |
| P0 | 年份/区域仲裁（显式过滤或同版本优先） | 解决 7 条「版本互相抢答」 |
| P1 | 过滤槽位收敛：`crop`→多值 `crops`，`growth_stage` 不默认硬过滤，空结果逐槽位放松 | 兼顾精度与召回 |
| P1 | 开启 Reranker 复测口语集 MRR@1 | 针对 37% 的 top-1 失败 |
| P2 | 补农事俗语词典 + 查询扩展 | 提升口语问法召回 |
| P2 | 负例题策略落地（硬拒答 or 标注来源的联网补充） | 降低幻觉风险 |

## 10. 一句话总结

这个项目真正有价值的不是「接了大模型」，而是三件事：

1. **把中文与农业领域的坑一个个填了**（token 估算、分词、别名、多版本、单值元数据）；
2. **让每个结论都有证据**（引用到文件页码、评测到 Recall/MRR、过滤到 `relaxed` 标记）；
3. **让工程能长期维护**（纯规则领域层、非破坏脚本、可消融的检索配置、238 个不依赖模型的测试）。
